# CPU模拟吞吐与内存实测

2026-11-15，在本机双路Xeon Gold 6330上测量训练所用的`stg_rl 0.4.7 / ENGINE_VER 35`。本轮只运行模拟，没有启动训练或租机。原始三轮数据、机器信息与内存快照见[汇总JSON](practice-cards/reports/2026-11-15-cpu-simulation-profile.json)。

主要结果：约678颗直线弹的稳定场景中，一个CPU硬件线程批量推进64个环境，合计约5.95万环境帧/秒；单进程28个物理线程约69.2万；两个进程分别绑定两路CPU、各28线程，合计约133.6万。4096个原生环境实测约5.87GiB RSS，换成正式668训练起点卡池后约5.91GiB。以上均不含神经网络推理、PyTorch包装、PPO和渲染。

## 比较口径

- CPU为2×Xeon Gold 6330，单路28物理核，共56物理核／112硬件线程。单线程实验将Python主线程和唯一Rayon工作线程都绑定到CPU2，只能消耗一个硬件线程的核时间；实际进程CPU时间／墙钟约1.00。
- 本机是共享服务器，测量时系统负载约29–34；cgroup v1 CPU配额为`-1`，没有CPU时间限额。绑定CPU不代表独占，三轮中位数和范围均保留，不能将本机结果直接当作其他CPU型号的速度。
- 每个世界帧按一份环境推进一帧计数：`FPS = 环境数 × step调用数 × frame_skip / 墙钟秒`。多环境结果是合计环境帧率，不是每个环境分别达到该速度，也不是向量批次的调用次数。
- 常规吞吐均为`frame_skip=1`，每帧完成世界推进、碰撞／脚本／生命周期处理以及原生RL观测、CSR压实和Python接口返回；不做观测的PyTorch解码、模型特征化、策略推理、reward或PPO更新。计时不包含编译、建场、预热和采样统计。
- 观测上限1024颗；世界继续模拟全部弹。主控制场景每帧发6弹，弹在上半场横穿、不会打中自机；先预热256帧，稳定约678弹，避免开局空场或死亡反复reset导致的虚高数字。自机持续射击，其他世界系统照常推进。
- 这是稳定直线弹负载，不代表复杂xform、激光重场或训练策略活到后期的所有局面。另测六张真实卡，但固定不移动的动作会早死／reset、弹量较低，只用作辅助对照。

## 一个硬件线程能跑多少帧

下表均为一个硬件线程，三轮中位数；括号是三轮范围。批量列包含64个独立世界，仍只用一个Rayon工作线程。

| 稳定敌弹数 | 单个环境逐帧调用 | 同核批量64环境，合计帧/秒 |
| ---: | ---: | ---: |
| 113 | 24,322（24,126–27,918） | 159,677（157,789–160,832） |
| 678 | 21,035（17,853–26,371） | 59,468（57,314–60,052） |
| 1,356 | 14,497（13,722–16,238） | 23,975（23,307–24,198） |

1356弹场景每帧平均约332弹未进入1024行观测，但世界积分与碰撞仍处理全部1356弹。它同时触发最近集合筛选，和未超cap的678弹场景并非纯粹的弹数倍增关系。

单局逐帧调用存在明显的Python／FFI／Rayon交接与观测成本；批量可以摊薄这些开销。因此向同行引用时，建议报“单硬件线程、64环境、约678弹、每帧观测，约5.9万环境帧/秒”，同时保留单局约2.1–2.4万帧/秒的数字。

### 世界推进与接口／观测的分离估计

另用更长的32768世界帧，改变一次接口调用内部推进的帧数。世界仍逐帧计算；只降低导出观测／调用Python的频率。

| 每次调用推进帧数 | 实际世界帧/秒，中位数 | 每世界帧耗时 |
| ---: | ---: | ---: |
| 1 | 24,375 | 41.03µs |
| 4 | 58,592 | 17.07µs |
| 16 | 84,938 | 11.77µs |
| 64 | 96,252 | 10.39µs |
| 256 | 101,753 | 9.83µs |

五档最终帧号均为33024，最终有效观测逐字节一致；校验只覆盖有效行，排除固定容量缓冲里未使用的旧尾行。对`每帧耗时 ≈ C + O / frame_skip`拟合，得到世界逐帧部分约9.70µs，约10.3万帧/秒；每次调用／导出额外项约31.23µs。**这是同一轨迹上的分离估计，不是直接关闭观测后测得的纯内核结果。** 额外项还包含线程交接与Python接口，不能全部归为观测编码。

256帧调用不能用来宣称策略每帧做决策时也有10万FPS；正式训练参数未改变。

## 多核与双路扩展

固定512个环境、每帧生成观测，每配置三轮、每轮256次向量step。下表为三轮中位数，单位为合计环境帧/秒。

| 工作线程／CPU布局 | 约678弹 | 约1356弹 | 六张真实卡固定动作，约83弹 |
| --- | ---: | ---: | ---: |
| 1个物理线程 | 47,844 | 20,548 | 136,972 |
| 2个物理线程 | 89,803 | 39,038 | 264,148 |
| 4个物理线程 | 168,404 | 76,526 | 510,613 |
| 8个物理线程 | 319,797 | 140,310 | 796,514 |
| 16个物理线程 | 540,605 | 231,278 | 1,106,297 |
| 28个物理线程，单路 | 691,909 | 290,352 | 1,231,012 |
| 56个物理线程，双路单进程 | 544,518 | 271,395 | 778,234 |
| 112个硬件线程，双路含SMT | 441,335 | 271,817 | 580,767 |

678弹场景从1到28线程加速14.46倍，按28线程计算效率约51.7%。单进程继续跨两路没有收益，SMT也不能按新增物理核理解。另将28线程放到双路各14个物理核时约48.2万FPS；放到单路14核的28个SMT线程时约55.9万，均低于单路28个物理核的69.2万。

再把同样512个环境拆成两个独立进程，每进程256环境／28线程，分别绑定CPU0–27和28–55。两边建场和预热后通过屏障同时开始计时，三轮并发吞吐之和为87.5万／133.6万／139.8万FPS，中位133.6万。每进程1024次step；导出观测的频率与单进程扫描相同。

这说明独立世界有充分的并行潜力；跨路时，进程分组、内存位置和调度方式会影响是否吃到第二路CPU。当前结果支持继续研究按NUMA分组，尚未将分组采样接入训练器。内存带宽、远端访问和公共调度的各自占比没有通过硬件计数器进一步区分，不能据本次结果指定唯一原因。共享机的首轮波动较大，133.6万只作为本机短测中位数。

六张真实卡为TH06六面`b6/mb2`和TH16六面`b2/b4/b6/b14`，均rank2；固定动作不是已训练策略，83弹也不是正式训练期间的平均弹数。

## 内存

独立子进程使用NumPy原生缓冲，不导入PyTorch。缓冲全部写入后建场并预热，读取RSS／USS／PSS；虚拟地址保留量不当作实占内存。

| 环境数 | 稳态RSS | USS |
| ---: | ---: | ---: |
| 1 | 36.92MiB | 27.51MiB |
| 64 | 129.57MiB | 120.19MiB |
| 256 | 409.32MiB | 399.93MiB |
| 1024 | 1,528.61MiB | 1,519.22MiB |
| 4096 | 6,005.69MiB，即5.87GiB | 5,996.30MiB |

拟合为`RSS ≈ 36.0MiB + 1.45745MiB × 环境数`。其中对外原生观测缓冲约62.6KiB/环境，4096环境约250.4MiB；其余主要是各环境世界状态和内部工作缓冲。固定池使空场也有基础成本，不能按当前活弹数把这部分内存等比例缩小。

额外加载正式686份材料、668个训练起点，原生4096环境实测RSS约5.906GiB，和单场景估计接近。该补测仍不包含PyTorch解码、策略、优化器与rollout，且没有模拟完整训练课程／策略。

只对原生部分外推：8192环境约11.7GiB，10000环境约14.27GiB；超出实测4096的数字是估计。训练总内存需另加框架、模型和采样缓冲，GPU显存也单独计算。

## 复算与交付

本机原始结果、脚本与日志：`runs/simulation-profile-20261115/`。便携结果包：`dist/cpu-simulation-profile-20261115.tar.gz`，含本报告、机器信息、49组原始结果、聚合JSON、控制场景ECL和复算脚本，不包含原作游戏源或权重。

解包后可对已安装本项目依赖的机器运行，例如：

```bash
STG_PROFILE_REPO=/path/to/stg-rl-train \
  /path/to/stg-rl-train/.venv/bin/python /path/to/bundle/measure.py \
  --workload dense6 --envs 64 --threads 1 --cpus 2 \
  --steps 512 --repeats 3 --output /tmp/sim-single-thread.json
```

换机器后按实际CPU亲和性修改`--cpus`，并重新核对CPU配额。`real6/fullpool`还需要本阶段的本地临时卡池；独立的`dense1/dense6/dense12`控制场景不需要。两份supervisor保留为本机命令记录，复算其他机器以`measure.py`为入口。
